# Prismalama dev plan — 22 Mar 2026

**Audience:** AI agents and humans continuing this work. **Do not** edit `.env` or secret-bearing files unless explicitly asked.

---

## Product goals (what “done” means)

1. **Ollama-like UX** for local inference on modest hardware; **Vulkan** (GGML) for broad GPU support; **ROCm/HIP** for AMD GPU inference where built.
2. **Weight streaming** for oversized models: AirLLM (PyTorch) for HF-style trees; GGUF via llama.cpp with mmap/streaming where applicable.
3. **Faithful shipping:** integration tests for promised behavior → **Arch package** (`PKGBUILD` / `build-rocm.sh`) when the installable artifact changes.
4. **Kubernetes-friendly GPU runtime:** reproducible container with GGML backends + `ollama` binary, no host install required; GPU via device plugin / device nodes.

## Next steps (implement in order unless blocked)

### A. GPU image hardening (high value)

1. **Multi-stage or slim runtime (optional):** reduce image size if the full `*-complete` dev base is too heavy for registry pulls; keep HIP + Vulkan + minimal ROCm runtime deps; verify `ollama` still finds all `.so` under `OLLAMA_LIBRARY_PATH`.
2. **CI hook:** add a **non-default** or **manual** CI job that runs `docker build -f docker/gpu/Dockerfile` (cache layers; may need long timeout). Do **not** make default PR CI depend on multi-hour GPU builds without runner capacity.
3. **Smoke script:** e.g. `scripts/docker-gpu-verify.sh` — build tag `prismalama-gpu` (or `SKIP_BUILD=1`), `docker run --rm … --version`, optional `list` if server started (document **no GPU in CI** → client-only checks).
4. **`.dockerignore`:** extend only if build context is still huge; align with `docker/test` patterns; do not exclude sources needed for `go build` + CMake.

### B. Kubernetes production readiness

1. **Registry workflow:** document `docker tag` / push and replace `image:` in example manifest; add **imagePullSecrets** example if private registry.
2. **Device plugin:** replace generic `amd.com/gpu` text with pointers to **your** cluster’s AMD GPU plugin resource name and **node selectors** / taints for GPU nodes.
3. **Models PVC:** swap `emptyDir` in example for `PersistentVolumeClaim` pattern; document `OLLAMA_MODELS` / host paths.
4. **SecurityContext:** document when `privileged` or extra caps are required vs device-plugin-only injection (cluster-specific).

### C. NVIDIA / CUDA variant (separate track)

Current GPU image is **AMD ROCm + Vulkan**. If product goals require **NVIDIA**:

1. New `docker/gpu-nvidia/Dockerfile` (or build-arg flavor) on **`nvidia/cuda`** + matching CMake `-DLLAMA_CUDA=ON`, `-DLLAMA_HIPBLAS=OFF`, runner dir naming consistent with Ollama conventions; **do not** break AMD path.
2. K8s example using **`nvidia.com/gpu`** and NVIDIA device plugin docs.

### D. Product and ship bar (ongoing)

1. **Integration tests** for any new user-visible behavior (`go test -tags=integration`, extra tags as in `integration/TEST_README.md`).
2. **`make ship-check`** before releases; bump **`PKGBUILD`** `pkgrel`/`pkgver` when the shipped package should change.
3. Keep **`docs/DEVELOPER.md`** and **`AGENTS.md`** in sync when workflows move.

### E. AirLLM inside GPU container (if required)

The GPU image today is **Go + GGML**; AirLLM needs **Python + PyTorch (ROCm)**. If the goal is **one** image for both:

1. Add a **separate stage** or **derived Dockerfile** installing minimal Python + `torch` ROCm + deps per `PKGBUILD` optdepends; size and maintenance cost are high — confirm with maintainers before doing.
